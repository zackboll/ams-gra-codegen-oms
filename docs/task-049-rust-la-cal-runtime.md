# Task 049 — Rust LA-CAL runtime adapter (backed by Sleet)

Task 049 is the first Phase 3 implementation slice. It adds the first
concrete runtime behind the Task 048 façade, in Rust only:

```text
generated Rust service API           (service-generate; application calls unchanged)
        |  PublishAdapter / SubscribeAdapter        crates/runtime-api-rust
        v
ams-gra-oms-runtime-rust             crates/runtime-rust
        |  OmsJsonCodec<P>  -- payload body only (caller-supplied)
        |  global-element envelope, SIDs, PUB/SUB/UNSUB, MSG dispatch
        v
sleet-client @ e38f61d8              pinned git dependency, not copied
        |  OWP over WebSocket (Sec-WebSocket-Protocol: owp)
        v
Sleet (or any LA-CAL server)
```

```text
Task 048:  generated type-safe operation
Task 049:  first reusable runtime executing that operation through real LA-CAL
Task 050:  generated OMS JSON payload codecs / broader runtime integration
```

Not in this task: generated field-by-field OMS JSON codecs (so no
`PositionReport` codec), the Ada and C++ LA-CAL runtimes, automatic
reconnect/backoff, TLS/auth policy beyond what `sleet-client` does, timers or
periodic publication, and service lifecycle policy.

* **Subprotocol** (§5.1, Table 5.1-1, CERT LACAL-000003/-000004): the client

* `MSG <subscription id> <message>`.

## 5. Codec boundary versus runtime envelope

```text
runtime (generic; depends only on the message QName):
    QName -> oms_global_element_name -> global JSON member and SUB message name
    exactly-one-member wrap on publish, exactly-one-member check on MSG
    PUB / SUB / UNSUB / MSG, subscription IDs, dispatch by SID, connection

codec (OmsJsonCodec<P>; one provider serves many P):
    payload fields and values only
```

Generated model types do not need to implement Serde. One provider type
implements `OmsJsonCodec<A>`, `OmsJsonCodec<B>`, and so on; the test codec
serves three payload types from two schemas. Task 050 can fill this seam with
generated codecs.

**One LA-CAL name formatter.** `oms_global_element_name(namespace, local)`
returns `local` when `namespace` is exactly
`https://www.vdl.afrl.af.mil/programs/oam`, and `{namespace}local`
otherwise. Near-miss URIs (a trailing `/`, or `http:`) count as ordinary
namespaces, and an empty namespace yields `{}local`. That one function
produces the outgoing JSON member, the expected incoming member, and the
`SUB` message name. There is no second copy.

## 6. Publish, Subscribe, dispatch

**Publish**: `codec.encode_payload(value)` →
`{ oms_global_element_name(ns, name): body }` →
`CalClient::publish(topic, &json)`. The key never comes from the payload
type, the topic, or a Rust type name.

**Subscribe**: allocate a SID → `CalClient::subscribe(sid,
oms_global_element_name(ns, name), topic, group)` → register a dispatch entry
keyed by the SID → return a `SubscriptionHandle`. If `sleet-client` rejects
the SUB, nothing is registered.

**MSG**: look up the SID. It is the only dispatch key; topic, message name,
and JSON shape are never used to pick a handler. Then parse the JSON, require
an object with exactly one member, require that member's key to equal the
subscribed LA-CAL name, pass only its value to `decode_payload`, and call the
handler with `&P`. Any failure becomes a
`RuntimeEvent::SubscriptionDecodeError`: the handler is not called and **the
subscription stays active**. The reasoning: a malformed publication from some
other service should not silently unsubscribe this one, and OWP gives the
receiver no per-message negative acknowledgement to send anyway.


## 7. Worker, subscription IDs, unsubscribe, shutdown

```text
application threads --(blocking call)--> bounded command channel (capacity 64)
    --> background OS thread "ams-gra-oms-lacal"
        current-thread Tokio runtime
        one sleet_client::CalClient (never shared, never behind a mutex)
        select! { shutdown | next command | client.recv() }   (unbiased; see §13)
```

This follows the public AMS GRA Rust examples, which run the async Sleet
connection on a background thread that owns a Tokio runtime. There is no
per-call `block_on`: each operation sends one command and waits on a oneshot
reply. The capacity of 64 bounds memory; since every caller waits for its own
reply, the queue holds at most one command per concurrently calling thread.
The event channel is unbounded, so events are never dropped and never
back-pressure the receive loop.

* **`connect`** returns only after the WebSocket upgrade and `INIT`/`INFO`
  succeeded on the worker, within `connect_timeout` (default 10 s). On
  failure the worker is joined before the error is returned.
* **Subscription IDs** are connection-local and monotonic: `sub-1`, `sub-2`,
  … Each is a legal OWP identifier and is never reused; a SUB rejected
  locally still uses up its number. Overflowing `u64` gives
  `SubscriptionIdsExhausted` and never wraps. IDs are not derived from
  function IDs, exchange IDs, topics, or message names.
* **Unsubscribe**: `SubscriptionHandle::unsubscribe(self)` consumes the
  handle, so a second call does not compile. The worker removes the dispatch
  entry **before** sending `UNSUB <sid>`, so a later `MSG` for that SID never
  reaches the old handler; it is reported as `UnknownSubscription`. Dropping a
  handle does not unsubscribe (the type is `#[must_use]`); explicit
  unsubscribe is the only policy.
* **Close / Drop**: `close()` signals shutdown, the worker drops the
  `CalClient` (which closes the connection), and the thread is joined. `Drop`
  does the same shutdown on a best-effort basis; it cannot report a worker
  panic. If the connection ends on its own, the worker emits
  `ConnectionClosed` and exits, and later calls fail with `WorkerStopped`.
  There is no reconnect.
* **Handlers run on the worker thread.** A panic in a handler or codec is
  caught and reported as `HandlerPanicked`, and dispatch continues. A handler
  that calls back into the runtime gets `CalledFromAsyncContext` instead of
  deadlocking.

## 8. Verbose versus non-verbose: non-verbose

Decision: `INIT` sends `"verbose": false`. Two reasons:

* In verbose mode the pinned `CalClient` waits for the status inside
  `publish`/`subscribe`/`unsubscribe`, and treats a `MSG` that arrives first
  as `UnexpectedServerOp("received MSG while awaiting status")`. The single
  worker must receive `MSG` continuously, so an ordinary interleaving would
  become an error.
* OWP `-ERR` carries neither the operation nor the SID, so it cannot be
  reliably paired with a request in any case.

The consequence, precisely: **an adapter `Ok` means the OWP frame was written
to the WebSocket, not that the server accepted it.** A later `-ERR` is
surfaced as `RuntimeEvent::ServerError { error, details }` and is never
dropped.

`RuntimeError` covers synchronous failures and is separate from
`CodegenError` and `ServiceApiError`. Variants: `InvalidConfig`,
`Codec(CodecError)`, `Client(Box<sleet_client::ClientError>)` (source
preserved; covers invalid topic/group/service/SID, transport failures, and
`INIT` rejection), `ConnectTimeout`, `WorkerSpawn`, `WorkerStopped`,
`WorkerPanicked`, `CalledFromAsyncContext`, `SubscriptionNotActive`, and
`SubscriptionIdsExhausted`.

`RuntimeEvent` covers asynchronous occurrences: `ServerError`,
`SubscriptionDecodeError { sid, message_name, error }`,
`UnknownSubscription { sid, payload }`, `HandlerPanicked { sid }`,
`ProtocolError` (an unparseable frame; the connection continues), and
`ConnectionClosed`. No logging dependency was added.

## 13. Corrective review: receive progress under command load (PR #50)

Reviewed head: `168782d281cdafbdf3bcaf423e938729385be6a1`. Sections 1–12
above describe that head and are otherwise unchanged.

**Finding.** `Worker::run` used `tokio::select! { biased; shutdown, commands,
client.recv() }`. A biased select polls branches in order on every iteration,
so whenever the command queue was ready, `client.recv()` was never polled. The
bounded queue does not prevent this: several application threads can keep it
refilled indefinitely. For as long as that lasted, `MSG` dispatch, late `-ERR`
events, and remote-close detection were all delayed without limit. That
contradicted the claim that receive processing continues while application
operations are active.

**Reproduction.** `worker::fairness_tests::
worker_receives_while_command_queue_is_continuously_ready` (a crate-private
unit test in `ams-gra-oms-runtime-rust`) drives the real `Worker` over a real
`CalClient` connected to a test-only OWP peer.

* Four threads keep the capacity-64 queue full: they call `blocking_send`
  without waiting for replies, which is the situation many concurrent callers
  create.
* After 500 `PUB` frames the peer sends
  `MSG sub-1 {"{urn:test}MessageA":{"Count":42}}` and
  `-ERR Illegal-State synthetic late error`.
* At the reviewed head the test **failed**: `Err(Timeout)`, the `MSG` was
  never dispatched within the 5 s bound. With a single flooder it passed,
  because the queue briefly drains between sends. Four flooders are needed to
  keep it continuously ready.

**Correction.** The only production change is removing `biased;`. With an
unbiased select, Tokio starts polling at a random ready branch on each
iteration, so neither side can starve the other.

* Commands-first (the old order) starves receive.
* Receive-first would starve commands when the socket stays readable, which is
  why it was rejected.
* Shutdown needs no priority. Its branch is still polled on every iteration,
  and each command or dispatch completes before the next select.
* A dropped `CalClient::recv` future is safe. It was already dropped whenever a
  command won under the old order. The pinned client suspends only in
  `WebSocketStream::next`, which is cancel-safe (a partial frame stays buffered
  in tungstenite), or while answering a `Ping`. A frame it has read is returned
  without another suspension point.

Unchanged: one worker OS thread, one current-thread runtime, one `CalClient`,
capacity 64, non-verbose OWP, `sub-N` IDs, SID-only dispatch, consuming
